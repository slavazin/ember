# Remediation is a default loop stage; its fix lands through the human merge as a write distinct from the corpus deposit

## Context
The fast loop boots a session, diagnoses through the `investigate` skill, and closes
through the `close` skill. The agent instructions and both loop-half skills name an
implementation phase between diagnosis and close, but no skill enacted it — a diagnosed
incident had no procedure to resolve it, so a session could freeze a diagnosis and close
without the fix the diagnosis warrants. ADR-0010 settled that a sandbox remediation is
gated at the pull-request merge, not by a harness tool-approval, on the premise that the
sandbox's only durable output is the corpus write it emits. A remediation to a service
surface breaks that premise: the fix to the service is a durable output too, and it is
not a corpus write — signing it with the corpus deposit's `Incident-*` trailers would
read it as a learning entry where the delta is read out of git history. ADR-0009 settled
that a sandbox write leaves as a patch the host applies, but the host helper it built
(`tools/patch-to-pr.sh`) admits only fully-signed corpus deposits.

## Options considered
### Option A — remediation stays ad hoc, outside the named loop stages
Shape: leave diagnosis as the loop's terminal work product and let any fix happen
outside the skills. Verdict: rejected — an incident responder that stops at a diagnosis
resolves no incident, and an unnamed stage carries none of the sandbox-trial and
merge-gate discipline the constitution requires of a fix.
### Option B — remediation is a default loop stage, its fix a distinct human-gated write
Shape: a diagnosis flows by default into a remediation procedure that trials the fix in
the sandbox against a frozen acceptance check and proposes it for the human merge, as a
write distinct from the corpus deposit. Verdict: chosen — it gives the named
implementation phase a procedure, keeps ADR-0010's merge gate rather than adding one, and
keeps the learning delta readable by separating the operational fix from the signed
deposit.
### Option C — the remediation is filed as a corpus deposit
Shape: the fix rides the same signed deposit path as the learning candidate. Verdict:
rejected — an operational fix signed with the deposit's `Incident-*` trailers reads as a
learning entry where the delta is read out of git history, polluting the one record
Article 12 rests on.

## Decision
Remediation is the default loop stage between diagnosis and close, carried by the
`implement` skill: a diagnosis flows into a fix aimed at the diagnosed cause, trialed in
the sandbox against an acceptance check frozen before the trial, and proposed for the
human merge. It is not gated by a harness tool-approval; the sandbox is disposable, and a
remediation's durable effect reaches the estate only through a human-gated pull-request
merge (superseding ADR-0010's narrower "only through a corpus write" — the merge admits
either a corpus deposit or an operational fix to the service). The default is bounded by
reach — a diagnosed cause with no in-estate lever closes on its escalation and mitigation,
not a forced local change. The remediation proposal is a write distinct from the corpus
deposit: it carries no corpus-deposit signature, so an operational fix is never mistaken
for a learning entry, and the host path that admits it is separate from the deposit-only
helper, which is not weakened to carry an unsigned fix.

## Consequences
Gives the named implementation phase a procedure and makes resolving the incident the
standing outcome, not an optional one. Keeps ADR-0010's merge gate rather than adding one:
the fix reaches the estate only through the human merge, and no agent touches a live
surface or merges its own fix. Keeps the learning delta readable by separating the
operational fix from the signed deposit. Forecloses a session closing on a diagnosis alone
when the cause has an in-estate lever, and forecloses signing a remediation as a corpus
deposit. Opens one build follow-up: the operational-fix host path — the emit, retrieval,
host-apply, and pull-request-open steps for an unsigned fix — is unbuilt, because the only
host helper (`tools/patch-to-pr.sh`) admits only signed corpus deposits; until it is built,
`implement` states the landing as a disclosed residue rather than an executable step.

## Warrant
- The loop names an implementation phase between diagnosis and close, discharged by the
  `implement` skill (as of 2026-08-29, skills/implement/SKILL.md,
  tenant-incident/agent/instructions.md).
- The remediation's sandbox trial and merge gate carry forward the decision this entry
  supersedes (ADR-0010); its patch-out shape rests on ADR-0009; its two-tier gate on
  ADR-0007.
- The deposit signature the remediation must not carry, and the deposit-only helper that
  must not be weakened to carry it, are the `Incident-*` trailer block and
  `tools/patch-to-pr.sh` (as of 2026-08-29, skills/corpus-write/SKILL.md, tools/patch-to-pr.sh).
- False if: a remediation's durable effect reaches the estate by a path that is neither
  the human merge nor otherwise human-gated.
- False if: an incident tenant moves to its own repository, where every write is agent
  output and the in-history deposit signature is moot (ADR-0015 Option A) — the
  fix-versus-deposit write separation reopens there.
- Revisit trigger `{when: the operational-fix host path is built, then: record the helper
  and its non-deposit validation on this entry's warrant, settled: }`.
