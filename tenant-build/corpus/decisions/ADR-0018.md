# Remediation is a default loop stage; its fix is a human-gated proposal, a distinct write from the corpus deposit

## Context
The fast loop boots a session, diagnoses through the `investigate` skill, and closes
through the `close` skill. The agent instructions and both loop-half skills name an
implementation phase between diagnosis and close, but no skill enacts it — a diagnosed
incident had no procedure to resolve it, so a session could freeze a diagnosis and
close without the fix the diagnosis warrants. ADR-0010 already settles that a sandbox
remediation is gated at the pull-request merge, not by a harness tool-approval, and
ADR-0009 settles that its durable effect leaves the sandbox as a patch the host pushes;
what is unsettled is whether remediation is a standing stage of the loop at all, and
whether the fix it proposes is the same kind of write as the learning deposit the close
files.

## Options considered
### Option A — remediation stays ad hoc, outside the named loop stages
Shape: leave diagnosis as the loop's terminal work product and let any fix happen
outside the skills. Verdict: rejected — an incident responder that stops at a diagnosis
resolves no incident, and an unnamed stage carries none of the sandbox-trial and
merge-gate discipline the constitution requires of a fix.
### Option B — remediation is a default loop stage carried by its own skill
Shape: a diagnosis flows by default into a remediation procedure that trials the fix in
the sandbox against a frozen acceptance check and proposes it for the human merge.
Verdict: chosen — it gives the named implementation phase a procedure and inherits the
sandbox-and-merge gate (Article 5, ADR-0010) without adding a gate.
### Option C — the remediation is filed as a corpus deposit
Shape: the fix rides the same signed deposit path as the learning candidate. Verdict:
rejected — an operational fix signed with the deposit's `Incident-*` trailers reads as a
learning entry where the delta is read out of git history, polluting the one record
Article 12 rests on.

## Decision
Remediation is the default loop stage between diagnosis and close, carried by the
`implement` skill: a diagnosis flows into a fix aimed at the diagnosed cause, trialed in
the sandbox against an acceptance check frozen before the trial, and proposed for the
human merge. The default is bounded by reach — a diagnosed cause with no in-estate lever
closes on its escalation and mitigation, not a forced local change. The remediation
proposal is a distinct write from the corpus deposit: it lands through the same two-tier
push-and-merge gate (ADR-0007), and it carries no corpus-deposit signature, so an
operational fix is never mistaken for a learning entry.

## Consequences
Gives the named implementation phase a procedure and makes resolving the incident the
standing outcome, not an optional one. Inherits the merge gate rather than adding one:
the fix reaches the estate only through the human merge, and no agent touches a live
surface. Keeps the learning delta readable by separating the operational fix from the
signed deposit. Forecloses a session closing on a diagnosis alone when the cause has an
in-estate lever, and forecloses signing a remediation as a corpus deposit.

## Warrant
- The loop names an implementation phase between diagnosis and close, discharged by the
  `implement` skill (as of 2026-08-29, skills/implement/SKILL.md,
  tenant-incident/agent/instructions.md).
- The remediation's sandbox trial and merge gate rest on Article 5 and ADR-0010; its
  patch-out path on ADR-0009; its two-tier gate on ADR-0007.
- The deposit signature the remediation must not carry is the `Incident-*` trailer block
  (as of 2026-08-29, skills/corpus-write/SKILL.md).
- False if: a remediation's durable effect reaches the estate by a path that is neither
  the human merge nor otherwise human-gated.
- False if: an incident tenant moves to its own repository, where every write is agent
  output and the in-history deposit signature is moot (ADR-0015 Option A) — the
  fix-versus-deposit write separation reopens there.
