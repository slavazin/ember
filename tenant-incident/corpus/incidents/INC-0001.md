# orders timed out because a 5-connection pool saturated under load

## Incident
The `orders` surface returned gateway 504s under load while the upstream wait in nginx consistently hit the gateway read timeout. The service logs showed requests spending ~5s waiting for a DB connection, with `pool_acquire_timeout` on saturated requests and no datastore error. PostgreSQL itself showed no blocked locks and only moderate active query counts.

## Forecast
Before remediation, the probe predicted the issue was caused by connection pool saturation inside `orders`, not slow queries or locks. The observed result matched: pool wait collapsed to ~0 after increasing the pool size, `waiting` dropped to 0, and the gateway returned 200s instead of 504s under the same load.

## Root cause
`orders` ran as a single process with a PostgreSQL pool capped at 5 connections. Under load, the pool saturated (`in_use=5`, `waiting≈40`), requests serialized behind pool acquisition, and gateway requests timed out before `orders` could return headers. Raising the pool cap to 20 increased effective concurrency enough to clear the queue and eliminate the storm.

## Learning
For this class, check pool saturation first: a small single-process pool can look like a downstream timeout storm at the gateway. The operational lever is pool capacity, not process duplication. Related learning candidate: none.

## Evidence
- Gateway logs and probe output showing repeated 504s with upstream_time ≈ 2s.
- `orders-svc` logs showing `pool_wait_ms` near 5000 and `pool_acquire_timeout` before the fix.
- `GET /debug/pool` output before fix: `max=5`, `in_use=5`, `waiting≈40`.
- Post-change probe output: `max=20`, `in_use=8-9`, `waiting=0`, gateway `200=25`, `504=0`.
